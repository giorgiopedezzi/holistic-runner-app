# AI workout classifier

> Reference detail, loaded on demand. Rules that PREVENT a mistake live in `CLAUDE.md`;
> this file DESCRIBES how the system works. Reachable from CLAUDE.md's routing table.

## AI workout classifier
Classifies a **running** activity's `track_points` into one of six hardcoded categories, via **either a local Ollama instance or deterministic statistical rules** — never a cloud API, nothing leaves the machine either way. Added 2026-08-06, statistical method added 2026-08-07, **split into two independent, side-by-side results (2026-08-07)** — see "Two independent result slots" below.

- **Always on-demand, never wired into sync.** `sync-garmin.ts`/`sync-strava.ts` are untouched — Ollama latency is unpredictable, and this app already has a documented history of being burned by an external process blocking sync (the PowerShell MTP hang, see "Known issues" above). Classification only ever happens via an explicit button click (`ActivityModal.tsx`'s `ClassificationCard`) or a bulk action in Data & Sync (`ManageTab.tsx`'s `ClassifySection`).
- **`workout-metrics.ts`** (pure functions, no I/O — mirrors the `fit-parser.ts`/`sync-garmin.ts` split between pure logic and I/O) reduces raw `track_points` into a compact `WorkoutSummary` — never the raw per-second array itself goes into the prompt:
  - `computePaceStdDev` — stdev of per-point pace, excluding `speed_ms <= 0.05` (same threshold `ActivityModal.tsx`'s `metricValue()` uses — pace is undefined near zero, would blow up the variance meaninglessly).
  - `countZeroPaceEvents` — a **direct server-side port of `ActivityModal.tsx`'s `detectPausesFromTimestamps`/`detectPausesHeuristic`** (not a naive "speed near zero" scan) — this project already learned the hard way (see "FIT parser notes") that `timestamp_unix` gaps are the reliable signal for a real stop, with the speed-threshold heuristic only as a fallback for data without it (Strava, pre-backfill Garmin rows).
  - `computeSplits(points, splitMeters)` — buckets by cumulative `distance_m`; each split's pace is segment-duration ÷ segment-distance (not an average of instantaneous per-point paces). **`splitMeters` defaults to 1000 but is a real parameter** — reclassifying with `0.5km` splits instead of `1km` can surface short interval structure a coarser split smoothed out (verified live: the same reference activity classified as `Repeats/Intervals` at 1km splits and `Fartlek` at 0.5km splits — genuinely different signal, not a bug).
- **`integrations/ollama.ts`**: plain `fetch` to `${host}/api/generate` (`OLLAMA_HOST`/`OLLAMA_MODEL` env vars, required only when classification is actually invoked — e.g. `http://localhost:11434` / `phi3:mini`, a small model deliberately chosen over something larger since this is a narrow six-category classification task, not open-ended generation, and the bulk workflow means many sequential calls where per-call latency matters). Uses Ollama's real `format: "json"` parameter to constrain output, then **validates the returned classification string is exactly one of the six known labels** — a model drifting from the enum surfaces as a clean error, never a silently-persisted bogus value. A connection failure throws `"Ollama not reachable at <host> — is it running?"`, not a raw stack trace.
- **`stats-classifier.ts`**: a second, independent classification method — `classifyByStatistics(summary)`, deterministic rules over the exact same `WorkoutSummary` (pace stdev, splits, zero-pace events, distance/duration), **no LLM, no network call, instant** (~0.1s vs ~20s for Ollama on CPU). Deliberately uses no heart-rate thresholds — this app has no HR-zone/max-HR setting to make "Zone 1/2" well-defined statistically, and pace-variance/splits/pauses/distance/duration are sufficient to distinguish all six categories on their own (matches how the feature was actually requested: "through statistics and pause analyses," not heart rate). Rule order (most-specific/unambiguous signal checked first): `zeroPaceEvents >= 2` → Tapasciata; ≥70% of consecutive splits getting faster → Progressive Run; high pace-variance (`stdev >= 0.5 min/km`) *and* ≥50% of consecutive split-pairs reversing direction → Repeats/Intervals; high variance alone (didn't match the structured patterns above) → Fartlek; else distance/duration threshold (15km/90min) splits Long Session vs Recovery Run. All thresholds are hardcoded constants in `stats-classifier.ts` for now, not settings — same "start fixed, make configurable later if wrong" path the outlier-detection thresholds took.
- **Two independent result slots (2026-08-07 redesign)**: `ai_classification`/`ai_explanation` and `statistical_classification`/`statistical_explanation` are separate column pairs — running one method never overwrites the other's stored result, so both can exist at once and be compared. This replaced an earlier single-slot design where `ai_classification` held whichever method ran most recently (with `classification_method` recording which one produced it) — that made "compare AI vs statistical on this activity" impossible without reclassifying back and forth, overwriting the very thing you wanted to compare. Both slots are persisted as soon as they're computed, **before** any human review — a "pending" (unreviewed) classification is still a stored one, not held back until confirmed.
  - **One-time backfill on the same migration** (`db.ts`'s `addingStatisticalSplit` guard, runs exactly once when `statistical_classification` is first added): pre-split rows whose *last* classify call was `'statistical'` have their real result sitting in `ai_classification`/`ai_explanation` (the old shared slot) — without moving it, that result would render under the AI card post-split, not the Statistical one (a real bug hit on first use after this redesign — a plain `ALTER TABLE ADD COLUMN` doesn't relocate existing data, only creates the new empty columns). Fixed by moving `ai_classification`/`ai_explanation` → `statistical_classification`/`statistical_explanation` and clearing the old slot wherever `classification_method = 'statistical' AND ai_classification IS NOT NULL`. The same one-time step also NULLs `classification_method` on any row where `user_feedback IS NULL` — its old meaning ("which method last ran") no longer applies once it's repurposed to mean "which card the *confirmed* verdict came from," so a stale value on a still-pending row would otherwise make the frontend show a false "✓ confirmed" tag on whichever card happens to match. The frontend also guards against this independently (`isVerdictSource` requires `user_feedback != null`, not just a `classification_method` match) as a second layer, in case any other stale-data path surfaces the same symptom later.
- **One shared verdict, not one per method**: `user_feedback`/`user_correction_reason`/`final_classification` remain single columns per activity — there's exactly one confirmed answer, not an independent AI-verdict and statistical-verdict (an alternative design considered and rejected during planning, since it doubles the review workflow for a single activity's ground truth without a clear use case for "the AI was right but I trust the stats one" living at the same time as its opposite). `classification_method` was **repurposed**: it used to mean "which method produced `ai_classification`" (set at classify time); it now means "which card (`ai`/`statistical`) the confirmed verdict came from" (set at feedback time, via the `source` field on the feedback request). Thumbs up/down on either card's result sets that card as the source of the activity's one verdict — approving the Statistical card while the AI card also has a (different, unconfirmed) result just leaves the AI card visible for reference, unconfirmed.
- **Schema** (`activities` table, all nullable, `NULL` = not yet run): `ai_classification`, `ai_explanation`, `statistical_classification`, `statistical_explanation`, `user_feedback` (`'approved'|'rejected'|NULL`), `user_correction_reason`, `final_classification`, `classification_method` (`'ai'|'statistical'|NULL`, see above). **Not** part of `ActivityRow`/`activityParams()` — same reasoning as `deleted_at`/`purged`: populated by a separate later code path, not the sync insert path. **Status is derived, not stored**: both classification columns `NULL` → unclassified; at least one set but `user_feedback IS NULL` → pending ("yellow", `var(--accent-orange)`); `user_feedback` set (either value) → confirmed ("green"). `types/api.ts`'s `classificationStatus()` is the one place this logic lives, shared by `ActivityModal.tsx` and `ManageTab.tsx`.
- **Reclassifying is always allowed**, even on an already-confirmed activity, **independently per method** — each card's "Classify"/"Reclassify" button never locks. Reclassifying *either* method always resets the shared verdict (`user_feedback`/`user_correction_reason`/`final_classification`/`classification_method`) back to `NULL`/pending, even if the reclassified method wasn't the one the old verdict was sourced from — a deliberate simplicity choice over tracking whether the specific reclassified card was the confirmed one (see `classifyUpdateAi`/`classifyUpdateStatistical` in `server.ts`).
- **`ActivityModal.tsx`'s `ClassificationCard`** is now a thin wrapper: an overall status line (confirmed label, or "Pending review"/"Not yet classified") plus a shared split-size toggle (1km/0.5km, applies to whichever card's Classify button is clicked next), rendering two `MethodResultCard`s side by side (`flex-wrap`, so they stack on narrow widths) — one per method, each with its own independent classify button + loading state (so AI's ~15-25s doesn't block Statistical's ~0.1s, or vice versa), its own result + explanation, and its own thumbs up/down that feeds `source: method` into the feedback call. A card whose result is the activity's current confirmed source shows a green "✓" next to its label.
  - **Each card shows elapsed classify time** — a live ticking counter in the button itself while running (`Classifying… N.Ns`, updated every 100ms off a `startedAtRef` timestamp, not a fixed-interval estimate) so a ~15-25s AI call doesn't look frozen with zero feedback, plus a small "took N.Ns" note left in place under the button after completion until the next classify run. Purely client-side timing (wall-clock around the `api.garmin.classify` call), not measured/returned by the backend.
- **Routes**: `POST /api/activity/:id/classify` (body `{splitMeters?, method?}` — `method` is `'ai'|'statistical'`, defaults server-side to `'ai'`, though both of `ClassificationCard`'s buttons always pass it explicitly now) writes only that method's own column pair (`classifyActivity()` in `server.ts` branches to `q.classifyUpdateAi`/`q.classifyUpdateStatistical`) and resets the shared verdict. `POST /api/activity/:id/feedback` (body `{feedback, source: 'ai'|'statistical', correctionReason?, finalClassification?}`) — `'approved'` sets `final_classification` = the current value of *that source's* classification column (400 if that source hasn't been classified yet); `'rejected'` requires both a known `correctionReason` and a known `finalClassification` as before. Either way sets `classification_method = source`. `POST /api/activities/confirm` (body `{ids}`, bulk) prefers `ai_classification` when both slots are populated (`COALESCE(ai_classification, statistical_classification)`) — bulk classify only ever populates one slot per run (see below), so this only matters for a row separately classified with both methods via the single-activity view.
- **There is deliberately no bulk `/classify` route** — `ManageTab.tsx`'s `ClassifySection` loops `POST /api/activity/:id/classify` sequentially from the frontend instead, because it needs real per-item "Classifying N/M…" progress, which a single request/response bulk endpoint can't report mid-flight without NDJSON streaming (like `streamSyncScript`) — more machinery than this needed. (A bulk classify route was built once during implementation and then deliberately removed once this tradeoff became clear — don't re-add it without re-adding streaming too.)
- **Bulk classify (`ManageTab.tsx`) deliberately keeps its single AI/Statistical switch, unlike the single-activity view** — one method per batch run, not two buttons — explicitly decided over "bulk also computes both" to keep batch runtime/Ollama load unchanged (doubling every bulk run's Ollama calls for a comparison feature that matters more one activity at a time than across dozens at once).
- **The bulk list shows one pill per populated slot (`resultPills` in `ClassifySection`), never a single merged pill — including after confirmation.** An earlier version computed one `pillText = final_classification ?? ai_classification ?? statistical_classification ?? status` — since `??` always prefers the first non-null operand, once `ai_classification` was set it permanently won that fallback chain, so classifying with AI and then reclassifying the same row with Statistical updated `statistical_classification` correctly in the DB (confirmed live by querying it directly) but the pill never changed to show it — a real bug, not a display choice, caught because it looked identical to "reclassify silently did nothing." A second version fixed that but then collapsed *both* pills into a single "Confirmed: X" pill once `status === "confirmed"` — which hid whichever slot wasn't the confirmed one, even though it's still stored and still useful for comparison. **Fixed**: both slots always render their own pill (`AI: X` / `Stats: Y`) regardless of confirm state; only the confirmed slot's pill (matched by `classification_method`) gets the green border/color and a "✓" prefix, the other stays visible in its normal (orange-if-pending / muted-if-confirmed-elsewhere) color.
- **Bulk "Confirm selected" used to always confirm via AI, ignoring the method switch.** `confirmActivityById` (`server.ts`) originally used `COALESCE(ai_classification, statistical_classification)` — i.e. always prefer the AI slot whenever both were populated, with no way for the caller to say otherwise. Fixed: the route now takes `{ids, method?}` (same field/default as bulk classify) and `confirmActivityById` takes an explicit `$source` param, picking `final_classification`/`classification_method` from *that* slot specifically (`CASE WHEN $source = 'ai' THEN ai_classification ELSE statistical_classification END`, both in the `SET` and the `WHERE ... IS NOT NULL` guard) — verified directly against real activity id 199 (distinct AI: "Progressive Run" / Statistical: "Recovery Run" results) that confirming with `$source: 'statistical'` correctly sets `final_classification = 'Recovery Run'`, not the AI value. The frontend's `confirmSelected()` now passes the switch's current `method`, and `canConfirm`/the button label are scoped to that same method's slot rather than "either slot populated."
  - **This fix appeared not to work at first** — turned out to be two stray backend processes (`node src/server.ts` plain, and a separate `server:watch`) both alive, with the *non-watching* one holding port 3001 and serving stale pre-fix code indefinitely (`--watch` only reloads a script on file change, it doesn't retry binding a port it lost at its own startup). Confirmed by checking `Get-NetTCPConnection -LocalPort 3001` for the owning PID, not by re-reading the source (which was already correct). Worth checking for a duplicate/stale process bound to 3001 first if a verified-correct fix still doesn't seem to take effect.
- **Bulk confirm used to reset the scrollable activity list's scroll position to the top.** `confirmSelected()` called `load()` to refresh, but `load()` toggles `loading`, which gates the entire scrollable list behind `{!loading && ... && (<>...)}` — so every confirm unmounted and remounted that whole block, including the scroll container, discarding its scroll offset. `classifySelected()` never had this problem since it patches `activities` in place via `updateOne()` without touching `loading`. Fixed by adding `refresh()` — the same fetch as `load()`, but without the `loading` toggle, so the container stays mounted and the browser preserves its scroll position like any other in-place DOM update — and switching `confirmSelected()` to call it instead.
  - **"Mark where you are"**: since scroll position is now preserved but the confirmed rows' checkboxes still clear immediately (the existing `useEffect(() => setSelected(new Set()), [activities])`, unchanged), there'd be no visual trace of what a confirm just did. `justConfirmed` (a `Set<number>`, set to the just-confirmed ids on success, cleared after 3s via a `setTimeout` ref) drives a green background flash-then-fade on those specific rows (`transition: "background-color 2.5s ease-out"` so the clear-to-transparent animates instead of cutting instantly). Uses `color-mix(in srgb, var(--accent-green) 18%, transparent)` — the first use of `color-mix()` in this codebase — specifically because the existing hex-alpha-suffix trick (`${color}22`, used by `ui.tsx`'s `Badge`, see "Activity detail chart" above) only works with literal hex strings, not this file's `var(--accent-*)` custom properties; `color-mix()` is the correct way to blend a CSS variable with transparency.
- **Correction reasons** (`CORRECTION_REASONS`, duplicated between `server.ts` and `types/api.ts` — no shared package between the two npm projects, same as `WORKOUT_CLASSIFICATIONS`/`SPORT_COLOR`): `"Warmup/cooldown skewed data"`, `"Perception felt harder than numbers"`, `"Traffic/Stops disrupted pace"`, `"Other"`.
- **Scoped to `sport === 'running'`** — the six categories (Fartlek, Progressive Run, Repeats/Intervals...) are running-specific terminology. `ClassificationCard` only renders for running activities; `ClassifySection`'s activity list is filtered client-side to running. Applies to both classification methods.
- **Verified (typecheck only) 2026-08-07** for the two-slot redesign — both `garmin-stats/` and `garmin-dashboard/` `npm run typecheck` clean after the schema/route/UI changes; not yet re-exercised live against a running Ollama instance (the original single-slot version *was* verified live on 2026-08-06/07 against real reference activity id 200 — full AI round-trip ~20-23s, statistical round-trip ~0.1s finding this activity's documented pauses → `Tapasciata / Light Maintenance`, approve/reject/reclassify/bulk-confirm all behaving correctly — but that was before the column split, so it should be re-run against the new schema before considering this fully done).
