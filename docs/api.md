# API endpoints (server.ts — port 3001)

> Reference detail, loaded on demand. Rules that PREVENT a mistake live in `CLAUDE.md`;
> this file DESCRIBES how the system works. Reachable from CLAUDE.md's routing table.

**Machine-readable contract:** `garmin-stats/openapi.json` (served live at `GET /api/v1/openapi.json`,
rendered at `GET /api/v1/docs`) is the source of truth for exact request/response schemas and status
codes — this file is the human-readable index. The two must stay in sync (CLAUDE.md's routing-table
rule); this table exists for quick lookup, not as a second contract.

| `/api/v1/activity-types` | The fixed `activity_types` lookup (Training, Race 5km, Race 10km, Half-Marathon, Marathon), each with `min_distance_m` |
| `/api/v1/activities/races` | Race-type activities (`activity_type_id != 1`), full history, `{id,date_only,activity_type_id,activity_name,distance_m}` — feeds the "link a race" dropdown on the date-ranges save form |
| `/api/v1/date-ranges` | Saved named date ranges (paginated envelope), newest first — each row `LEFT JOIN`s its linked race activity's display fields (`race_date_only`/`race_activity_name`/`race_distance_m`/`race_activity_type_id`, all `NULL` if unlinked). See `docs/schema.md`'s `date_ranges` section |
| `/api/v1/locales/:lang` | Translation bundle for `:lang` (`en` or `it`) — flat key→string JSON, read live off `garmin-stats/locales/<lang>.json`, no envelope. `:lang` is whitelisted before touching the filesystem; `problem+json` 404 for an unsupported or missing language |
| `/api/v1/plan-templates` | Saved training-plan templates (paginated envelope), newest first. See `docs/schema.md`'s `plan_templates` section (HRA-112) |
| `/api/v1/plan-templates/:id` | Single plan template (includes `approved_at`, HRA-113) |
| `/api/v1/plan-instances?template_id=` | Resolved plan instances (paginated envelope), newest first (HRA-118) — added since the instance card needs a way to list more than one at a time; no prior endpoint returned a collection. `template_id` is optional (a "list all" vs. a per-template list); 404 if a given `template_id` doesn't reference a real template, 400 if it isn't an integer |
| `/api/v1/plan-instances/:id` | A resolved instance of a template — the instantiate response's own `Location` target — plus its `days` (all `plan_instance_days` rows, each with `segments` as JSON, its own `customized_at` (HRA-299, nullable), and its own stable `workout_id` (HRA-333, see `docs/schema.md`)), `approved_at` (HRA-113), `name`/`event` (HRA-114), `race_name`/`race_date`/`race_url` (HRA-121, all nullable), and `current_revision`/`original_revision` (HRA-336, see `docs/schema.md`) |
| `/api/v1/plan-instances/:id/reports/workouts/:workoutId?as_of=` | The single-workout/race report (HRA-336) for one planned workout, addressed by its stable HRA-333 `workout_id`. Reads Original, Current, their revisions, accepted HRA-334 association evidence, and `asOf` from one consistent application-level read boundary (`services/reporting.service.ts`) — reuses HRA-333's lineage classifier and HRA-335's shared metrics primitives rather than a second calculation engine. A workout counts as the plan's race day when its own placement date equals the instance's `race_date` (HRA-121); race actual comparison always uses elapsed time, never moving/active (the race clock doesn't stop). No official-result data source exists anywhere in this codebase yet — `race.actualSource` is always `'activity'` or `'none'`. `as_of` (optional query param, ISO instant) overrides the future/missed cutoff; defaults to server "now". 404 if the instance or workout doesn't exist. **HRA-337:** the response also carries Actual-only `hr`/`stamina`/`pauses` evidence (`domain/reporting/evidence.ts`) — `null` whenever there is no accepted activity, never a fabricated zero. `hr` is cheap (activities.avg_hr/max_hr only, duration-weighted across every accepted activity). `stamina`/`pauses` are read from `track_points` for the accepted evidence activities ONLY (never Original/Current, never the whole plan) — `stamina` is "the one recorded stamina series" (the first accepted activity's own series: first valid/finish/depletion-in-points/minimum/coverage, never assuming a 100% start); `pauses` reuses `domain/workout-metrics.ts`'s canonical `detectPauseEvents` (the same timestamp/heuristic detector `countZeroPaceEvents` already used) at the same 30s default threshold the frontend's own "Pauses (N)" dialog uses, giving pause count/longest/total-from-pauses plus a `details[]` (elapsed position, distance, duration, HR before/after/recovery-delta, stamina before/after, and `recorded`/`inferred` provenance) the frontend renders through the SAME `PauseInspectionDialog` an activity's own detail view already uses — no separate report-only pause UI. Aggregate/whole-plan HR/stamina/pause evidence (this Story's own "aggregate-ready evidence" and "comparable long-run/race rows" ACs) is NOT in this endpoint — out of this slice, see the HRA-337 review comment. See `garmin-stats/openapi.json`'s `WorkoutReport` schema |
| `/api/v1/plan-instances/:id/reports/weeks?section_name=&week_number=&range=&as_of=` | The week report (HRA-338) for one planned week, addressed by its own structural slot — `section_name` + `week_number` (`lineage.ts`'s own definition of a workout's placement, never a calendar-date span). Reuses HRA-335's shared `buildReport` engine (`domain/reporting/report.ts`) scoped to that week: a workout that moved into or out of this exact slot still surfaces as `moved_in`/`moved_out` (never silently dropped from one side), and `report.datasets`/`comparisons` are confined to this week's own days, never leaking the rest of the plan in. `workouts[]` labels every workout_id the week's own report references (`plan-report.ts`'s `buildWorkoutIdentities`, mirroring `WorkoutReport.identity`'s shape) so a caller can render "grouped by workout" without a per-workout fetch. `evidence` extends HRA-337's HR/stamina/pause rules to this week's whole accepted population: `hr`/`pauses` blend across every accepted activity in scope (HR is already duration-weighted; pause count/longest/total are sums/max, never averages); `comparableStamina` deliberately does NOT blend — at most one session (the week's race, else its own strict-max-actual-distance completed run, no unique winner meaning none) carries its own single-activity stamina series, never a blended depletion curve. `range` (`plan_to_date` default, or `full_plan`) and `as_of` behave exactly as they do for the whole plan (AC4). 400 for a missing/non-integer `week_number` or an invalid `range`; 404 if the instance doesn't exist, or if this `section_name`/`week_number` never existed on either side of this instance. See `garmin-stats/openapi.json`'s `WeekReport`/`ReportResult`/`AggregateEvidence` schemas |
| `/api/v1/plan-instances/:id/reports/plan?range=&as_of=` | The entire-plan report (HRA-338): the whole plan's own isolated Original/Current/Actual totals (`overall`, plus its own `overallEvidence`) alongside a per-week breakdown (`weeks[]`, chronologically ordered by each week's own earliest known date) for progression, each with its own isolated `report`/`evidence` computed the SAME way the standalone week-report endpoint above would for that exact week (never a looser approximation). Every scope reuses HRA-335's shared `buildReport` engine — once for `overall`, once per week — never a second calculation engine. `range`/`as_of` apply identically to `overall` and every week; requesting the other `range` is a second call, never both at once in one response (AC "a completed/full-plan presentation remains distinct from plan-to-date"). An empty plan (no days on either side yet) returns an empty report rather than 404ing. 400 for an invalid `range`; 404 only if the instance itself doesn't exist. See `garmin-stats/openapi.json`'s `PlanReport` schema |
| `/api/v1/reports/range?from=&to=&range=&as_of=` | The date-range/race-range report (HRA-341) — cross-plan, unlike every report above. Scans every plan instance whose Original or Current span overlaps `[from,to]` and gives each its own isolated `buildReport` call (`domain/reporting/report.ts`'s new `dateWindow` filter), with associations pre-filtered to that instance's own workout ids so one instance's accepted evidence can never leak into another's totals within the same window (`services/reporting.service.ts`'s `getRangeReport`). `aggregate` sums datasets/denominators/drill-down across every included instance; its own Actual dataset, and the range-wide `unplanned`/`ambiguous` lists, are computed ONCE against every activity in the window (never summed per instance, never duplicated). `provenance.grouping` (`"workout"|"week"|"month"`, `domain/reporting/range-report.ts`'s `resolveRangeGrouping`) is an advisory hint mirroring the Overview & Trends preset ladder — the caller buckets the per-instance execution/outcome entries it already has, no second server-side bucketing. `qualityEvidence` (HRA-341's own quality-workout range rollup) reuses HRA-342's per-workout `buildCanonicalQualityStructure`/`buildStructuredQualityComparison` over every CURRENT run-type day in `[from,to]` classified as a quality kind — a session with no reliable segment alignment stays visible with `available:false`, excluded from `workoutsWithEvidence`/`segments.alignedWorkSegments`. A race-range is just a saved `date_ranges` row's own `{from,to}` resolved by the caller before this call — no separate race-range endpoint exists. `range`/`as_of` behave exactly as they do for the plan report. An empty window (no instances, no activities) returns an explicit empty report rather than 404ing. 400 if `from`/`to` are missing/malformed or `from > to`. See `garmin-stats/openapi.json`'s `RangeReport` schema |
| `/api/v1/plan-instances/active?date=YYYY-MM-DD` | The one **approved** (`approved_at` set) plan instance whose resolved days cover `date`, same response shape as `GET /api/v1/plan-instances/:id` above. Extends `daysByDateAndWorkoutType`'s pattern, no `workout_type` filter (a REST day is a real dated row too, HRA-124). `problem+json` 400 for a missing/malformed date, 404 when no approved instance's days cover it. Feeds "Your agenda"'s today-centered home view (HRA-248) |
| `/api/v1/plan-instance-days?date=YYYY-MM-DD` | Every `workout_type === 'run'` `plan_instance_day` matching `date`, across every plan instance (any `approved_at` state), each denormalized with its owning instance's `instance_name` — no envelope, just an array (possibly empty). `problem+json` 400 for a missing/malformed date. Feeds `ActivityDetailBody`'s same-day planned-vs-actual picker (HRA-206) |
| `/api/v1/plan-instances/:id/days/:dayId/fit` | Exports one resolved `plan_instance_days` row as a binary Garmin Workout `.fit` file, wrapping `toGarminWorkoutFit` (`garmin-stats/src/integrations/garmin-workout.ts`) — no parsing or persistence, so an approved instance is not guarded against. `Content-Disposition: attachment; filename="<instance name>_<YYYYMMDD>.fit"`. 404 if the instance or day doesn't exist; `problem+json` 422 (mirroring `toGarminWorkoutFit`'s own rejections) if the day is `needs_review` or its `workout_type` isn't `run`/`rest` (HRA-202) |
| `/api/v1/plan-instances/:id/fit?section_name=&week_number=` | Bundles every exportable day in a section (or, with `week_number`, one week within it) into a single uncompressed (STORE) zip via a zero-dependency writer (`garmin-stats/src/domain/zip/writer.ts`, `node:zlib`'s `crc32()`), reusing the day-fit endpoint's own `toGarminWorkoutFit` path per day. `section_name` is a required query filter (400 if missing), not a path segment — it's a free-text denormalized column, not an addressable sub-resource. A day `toGarminWorkoutFit` itself rejects (`needs_review`, or an unsupported `workout_type`) is skipped rather than failing the request; `X-Export-Total`/`X-Export-Included`/`X-Export-Skipped` response headers carry the counts since the body is opaque binary. `Content-Disposition: attachment; filename="<instance name>_<first date:yyyymmdd>-<last date:yyyymmdd>.zip"`. 404 if the instance doesn't exist; `problem+json` 422 if zero days in scope are exportable (no matching rows at all, or every match rejected) (HRA-203) |
| `/api/v1/activities/:id/association` | This activity's current planned-workout link (HRA-334) — `{activity_id, workout_id, status, instance_id, instance_name, section_name, week_number, date}`, all the plan-day/`status`/`workout_id` fields `null` when none exists yet — a legitimate "extra/unplanned" state, not a 404. 404 only when the activity itself doesn't exist. See `docs/schema.md`'s `workout_associations` section |
| `/api/v1/activities/:id/association-candidates` | Every `workout_type = 'run'` plan day (any instance) sharing this activity's own local calendar date — computed via the owning instance's `schedule_timezone` (HRA-332), never `activities.date_only` — the manual replace/confirm picker's option list. Same response shape as `plan-instance-days` above |

| Endpoint | Description |
|---|---|

| `/api/settings/background` | Body `{background_kind: 'none'\|'bundled', background_value?}` — selects a bundled preset or clears back to none. `background_value` required when `background_kind` is `'bundled'`. Uploading a custom image is a separate route (below), since that carries a binary body |
| `/api/settings/units` | Body `{unit_system}`, must be `'metric'`, `'imperial'`, or `'auto'` (400 otherwise). Same immediate-apply pattern as theme |
| `/api/settings/detail-view` | Body `{activity_detail_view}`, must be `'accordion'` or `'modal'` (400 otherwise). Same immediate-apply pattern as theme/units |
| `/api/v1/settings/date-format` | Body `{date_format}`, must be one of `'numeric_uk' | 'numeric_us' | 'literal_uk' | 'literal_us'` (422 otherwise). Same immediate-apply pattern as theme/units/detail-view |
| `/api/v1/settings/language` | Body `{language}`, must be one of `'auto' | 'en' | 'it'` (422 otherwise). `'auto'` resolves from the browser's `navigator.language` at render time (garmin-dashboard's `i18n.ts`), same idiom as `unit_system`'s `'auto'`. Same immediate-apply pattern as theme/units/detail-view/date-format |
| `/api/v1/settings/palette` | Body `{palette}`, must be one of `'metal' | 'warm'` (422 otherwise). Dashboard palette flavor, crossed with `theme` for 4 total looks — applied via a `data-palette` attribute (garmin-dashboard's `index.css`), compounded with the existing `data-theme` attribute. Also writes the paired `accent_color` server-side (`metal`→`sky`, `warm`→`amber`) — see `settings.controller.ts`. `'metal'` is the default. Same immediate-apply pattern as theme/units/detail-view/date-format/language. Replaces the earlier `/style-pack` endpoint (HRA-119) entirely |
| `/api/v1/activities/:id/type` | Body `{activity_type_id, name?}` — full replacement of the activity's type/name sub-resource. 422 if the type is unknown or the activity's `distance_m` is shorter than the type's `min_distance_m`; 404 if the activity doesn't exist |
| `/api/v1/activities/:id/association` | Body `{workout_id}` — sets/replaces/confirms this activity's planned-workout link (HRA-334). 422 if `workout_id` doesn't name a current plan day (any `workout_type` — a manual override may legitimately point at a day that moved); 404 if the activity doesn't exist. `'manual_confirmed'` if `workout_id` is unchanged from what's already on record, `'manual_changed'` otherwise (including a first-ever manual pick) — both immune to later automatic reconciliation |
| `/api/v1/date-ranges/:id` | Body `{name, from, to, activity_id?}` — full replacement, incl. renaming (the Data & Sync tab's "Update" row). Same validation as `POST /api/v1/date-ranges` below, except the duplicate-name check excludes the row's own id (so re-saving under its current name doesn't 409 itself). 404 if the row doesn't exist |
| `/api/v1/plan-templates/:id` | Body `{name, event, distance_m?, dsl_source}` (HRA-120) — full replacement; `dsl_source` is re-parsed from scratch, `event`/`distance_m` validated the same as `POST /api/v1/plan-templates` below. 404 if the template doesn't exist. Always clears `approved_at` back to `NULL` (HRA-113 gate 2 — any edit revokes approval, even one that still parses with zero warnings) |

### PATCH
| Endpoint | Description |
|---|---|
| `/api/v1/plan-instances/:id` | Body `{name?, race_name?, race_date?, race_url?, days?}` — partial update (HRA-135, replacing the earlier PUT). All fields optional but at least one is required (422 if none supplied); each provided field replaces its current value, every omitted field is left untouched. `race_name`/`race_date`/`race_url` are nullable — send `null` to explicitly clear one. `event` is never accepted here — read-only/derived from the template. **`days`, when provided, still fully replaces the instance's resolved day set** (unchanged semantics from the old PUT, HRA-113 AC9/HRA-114/HRA-115) — each day is `{section_name, week_number, date, dsl, workout_id?}`, `dsl` the raw D-line text, same grammar as a template (e.g. `"D3 [interval]: 4x3000m @ RG-20 r:1km @ RG+10"`), not pre-resolved segments. **`workout_id` (HRA-333, optional)** is a caller-echoed stable identity — honored only when it names one of this instance's own *current* days (never trusted blindly), letting a day/week swap survive this wholesale delete+recreate without reading as an unrelated removal+addition; omitted (a genuinely new day) or unrecognized (stale/foreign), a fresh id is minted — see `docs/schema.md`'s workout-identity paragraph. The backend looks up that day's section/week in the source template's parsed plan for its effective `PacePolicy`, merges in the instance's own `pace_overrides`, re-parses the `dsl` against that policy, and resolves it the same way instantiation resolves a segment. Rejects with 422 (listing which days) if any day's fresh parse still needs review. Never touches or re-instantiates the source template. Clears `approved_at` back to `NULL` whenever any field in the body is applied, same gate-2 rule as the template PUT above. 404 if the instance doesn't exist (HRA-113, HRA-135) |
| `/api/v1/plan-instances/:id/days/:dayId` | Body `{dsl?, notes?, scheduled_time?, workout_id?}` (HRA-149) — a smaller, more honest write than the bulk `days` replace above: one field's worth of edit on one already-existing day, each field validated independently. `dsl`, when supplied, is re-parsed against this day's own existing section/week/date scope + the template's effective `PacePolicy` and resolved the same way the bulk days-replace path does; 422 if the fresh parse still needs review. **A `dsl` write also sets `customized_at` (HRA-299)** — the day-level customization marker (see `docs/schema.md`); `notes`-only or `scheduled_time`-only patches never do. `notes` overrides whatever the `dsl` parse itself produced for that field, when both are supplied together. `scheduled_time` is `HH:MM` 24-hour or `null` to clear back to the 08:00 display default. **`workout_id` (HRA-333, optional, an accessory field never counted toward "at least one required")** moves this row's stable identity onto the content it now holds — the swap flows that persist via two of these calls (`AgendaTab.tsx`, `MobileWorkoutSwap.tsx`) each supply the OTHER swapped day's `workout_id` alongside its swapped-in `dsl`; trusted as-given (no same-instance membership check here — see `docs/schema.md`). **No longer rejected once the instance is approved (HRA-249)** — HRA-126's edit lock is a frontend-only warning now; only activating a conflicting instance is hard-blocked (see the `approve` endpoint below). Never touches or re-instantiates the source template |

### POST
| Endpoint | Description |
|---|---|
| `/api/sync/garmin` | Spawns `sync-garmin.ts`, streams NDJSON progress events (`{type:"progress",phase,current,total,label}`), ends with `{type:"done",imported,skipped,errors}` or `{type:"error",message}` |
| `/api/sync/withings?from=&to=` | Spawns `sync-withings.ts` via `child_process.spawn` (passing `from`/`to` through as `--from`/`--to` CLI args if given), returns `{ imported, skipped, errors }` (blocking, single response). If `from`/`to` are omitted, the script falls back to its own default (since last synced measurement, or 2 years back on first run) |
| `/api/sync/strava?from=&to=` | Same pattern as Withings' sync route, spawns `sync-strava.ts`. `skipped` in the response folds in cross-source duplicates (see "Strava sync" below) |
| `/api/settings/background/upload?ext=jpg\|jpeg\|png\|webp\|gif` | Body is the **raw image bytes** (`Content-Type` set to the image's own mime type) — deliberately not `multipart/form-data`, since this app has zero runtime dependencies and a raw-body upload needs no parser at all (frontend just does `fetch(url, {method:"POST", body: file})`). Max 10MB. Writes to `garmin-stats/backgrounds/bg-<timestamp>.<ext>`, best-effort deletes the previous custom file (failure swallowed, not fatal), sets `background_kind='custom'` |
| `/api/activities/restore`, `/api/activities/purge` | Body `{ids: number[]}` (400 if empty/non-integers). Restore clears `deleted_at`; purge wipes the row's heavy data and sets `purged=1` — see "Soft delete & trash". Looped single-row prepared statements inside one transaction, not a dynamic `IN (...)` clause, so every bound value stays a real parameter |
| `/api/body/restore`, `/api/body/purge` | Same shape/semantics as the activities pair, for `body_measurements` |
| `/api/v1/date-ranges` | Body `{name, from, to, activity_id?}`. `name` must be unique (409 otherwise); `from`/`to` are `YYYY-MM-DD` with `from <= to`; `activity_id`, if given, must be a race-type activity (`activity_type_id != 1`) whose `date_only` is strictly after `to` (422 otherwise). Returns 201 + `Location` + the created row (with the joined race fields) |
| `/api/v1/plan-templates/generate` | Body `{dsl_source}`. Runs the same parse as `POST /api/v1/plan-templates` but **never persists** — returns `{plan, warnings}` (per-day warnings live on each `DayEntry`, `warnings` here is the plan-scoped ones only). 422 (with an `errors` list) only if the DSL fails to parse outright (`ParseResult.ok:false`); a plan with day-level warnings still returns 200. What a review UI calls on every edit before the user is ready to save (HRA-113) |
| `/api/v1/plan-templates/prompt-preview` | Body `{text, language?, event?, event_name?, distance_m?, unit?}` (HRA-326). Composes the canonical "Plan text → RunPlan DSL" AI conversion prompt via `composeConversionPrompt()` (`garmin-stats/src/domain/runplan/prompt-composer.ts`) — the same function a future real AI provider call (Epic HRA-36) will use, so preview and the actual send can never drift. Never persists; returns `{prompt}`. `text` is the pasted plan source (or the fixed attachment placeholder); every other field is optional context. Tag-like substrings in `text` (e.g. `</training_plan>`, `<system>`) are escaped so they can't terminate the envelope early or be read as new instructions. What the "Prompt di conversione" pipeline stage calls instead of the old frontend-local prompt template |
| `/api/v1/plan-templates/ai-generate` | Body `{text, language?, event?, event_name?, distance_m?, unit?}` — same context shape as `prompt-preview` above (HRA-329). |---|---|
| `/api/v1/activities/:id/association` | Explicitly marks this activity as not part of any plan (HRA-334) — a real row is kept (`workout_id = NULL`, `status = 'manual_changed'`), never a plain delete, so a later import can never silently re-attach it (Scope: "represent extra/unplanned activities truthfully"). 404 if the activity doesn't exist |
